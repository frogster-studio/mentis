# The database admits only the API

`apps/api`, connecting as `service_role` through its `sb_secret_*` key, is the only reader and writer of the project's data. The `public` schema carries three independent locks: row-level security enabled on every table, zero policies, and zero privileges for `anon` and `authenticated` — no table, sequence, or routine grants, and no schema `usage`. The schema is not recreated: TypeORM creates its tables in place, so the locking SQL revokes by hand what dropping the schema used to discard — schema `usage` and `create` from `public`, table privileges and default privileges from `anon` and `authenticated` — and grants schema `usage` and table privileges to `service_role` alone, so reaching a future object costs an explicit grant. Only routines still need an explicit revoke, Postgres granting `execute` to `PUBLIC` on every new function by system default; they end executable by `service_role` alone. The publishable key and any player JWT reach Supabase Auth and nothing else — sign-in, refresh, and JWKS live on a separate plane the revokes never touch. Account deletion is the API calling `auth.admin.deleteUser` with the guard-verified user id, the FK cascade from `auth.users` erasing the player tables; no security-definer function exists. Storage keeps its shape per [ADR 0001](0001-storage-bytes-never-transit-the-api.md): public CDN reads, API-minted signed-upload tokens, `storage.objects` with RLS on and no policies.

We rejected keeping owner-scoped RLS policies as defense-in-depth: the API bypasses RLS, so retained policies protect no API request — their only live effect would be holding a direct-PostgREST door open for player JWTs to write forged rows around the API's contract validation. Real depth is independent locks on the same deny, not a second authorization model kept half-alive.

## Consequences

- Every future table or function is born inaccessible from outside: a forgotten grant or missing policy fails closed, and re-opening direct access requires defeating all three locks at once.
- Score integrity rests entirely on the API's validation — no client-writable path to the player tables exists.
- The tables are encoded in `apps/api/src/_database/migrations/`, which is generated from the entities and holds no hand-written statement. Every lock, trigger and bucket lives outside the repo, applied once on the dashboard — so the locks are not versioned, and a new table stays unreachable by the API until its grant is run by hand.
- pg_graphql resolves against SQL privileges, so the auto-exposed GraphQL endpoint goes inert with no separate switch.
