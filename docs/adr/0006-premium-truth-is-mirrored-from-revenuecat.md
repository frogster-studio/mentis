# Premium truth is mirrored from RevenueCat

RevenueCat is the system of record for the Premium subscription, but the API must answer "is this Account premium right now" at the moment of an action — lapsed means free immediately, store grace periods count as active (the mobile glossary's Premium rule). So the API keeps one mirrored row per Account — `premium_entitlements`, `owner` unique, carrying `premium_until` and the `environment` that backs it — and every premium gate is the local compare `premium_until > now()`, never a RevenueCat call in the hot path. Webhooks never write state from their payload: delivery is at-least-once with no ordering guarantee, so an event (behind a constant-time check of the static `Authorization` header RevenueCat is configured to send) only *triggers* a re-fetch of that customer's current entitlements from RevenueCat REST, which overwrites the row. Idempotency, out-of-order retries and `TRANSFER` (a store restore moves the subscription to another app user ID and revokes the loser) all collapse into one upsert that always lands on current truth — RevenueCat's own recommended sync pattern.

We rejected push-only (deriving `premium_until` from event payloads saves the REST key and one call per event, but buys the ordering and TRANSFER reasoning forever), pull-per-check (RevenueCat's latency and availability between a Player and every gated action), and HMAC signature verification on the webhook (raw-body plumbing to protect a payload the design never trusts anyway — a forged but authenticated delivery can only trigger a re-sync). Both store environments count as premium for now: only dev and TestFlight builds can produce a sandbox purchase, and the map's end-to-end proof is precisely a sandbox purchase flipping the real gate; `environment` rides on the row so tightening after launch is a where-clause, not a migration. Mobile renders its own premium UI from the SDK's `CustomerInfo` (instant at purchase, offline-cached); the mirror gates server actions alone and is observable at `GET /app/me/premium` — after a purchase the app animates while polling that read until the webhook lands, and there is deliberately no client-triggered refresh write.

## Consequences

- The API gains two RevenueCat secrets in `env.config`: the webhook's static `Authorization` value and an `sk_` REST key.
- A delivery that exhausts all five webhook retries leaves the mirror stale until the next event for that customer; the RevenueCat dashboard's event log is the backstop, accepted for MVP scale.
- The new table gets the ADR 0003 locks (RLS on, zero policies) as hand-run SQL once the migration lands.
- Premium checks work with RevenueCat fully down — only the mirror stops refreshing.
