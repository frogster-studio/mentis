# RevenueCat under Expo: SDK, identity, webhooks, pricing

Research for #39 (wayfinder #38). Scope: single auto-renewable monthly €2.99 subscription "Premium", entitlement `premium`, purchase requires Supabase sign-in, custom paywall, Expo web out of scope but must not crash. **All sources accessed 2026-08-21.**

## 1. SDK: react-native-purchases with expo-dev-client

- Current version: **10.7.2**, published 2026-08-20 ([releases](https://github.com/RevenueCat/react-native-purchases/releases), via GitHub API). v10.0.0 (2026-04-15) moved to Play Billing Library 8.3.0 and raised Android minimum to API 23 ([v10.0.0 notes](https://github.com/RevenueCat/react-native-purchases/releases/tag/10.0.0)).
- Peer deps: `react-native >= 0.73.0`, `react-native-web` optional ([package.json](https://github.com/RevenueCat/react-native-purchases/blob/main/package.json)); README: "The minimum React Native version this SDK requires is `0.73.0`", minimum Kotlin 1.8.0 ([README](https://github.com/RevenueCat/react-native-purchases#readme)). No Expo SDK version matrix is published anywhere in the docs.
- Install: `npx expo install react-native-purchases` (plus `react-native-purchases-ui` only if using their paywalls — we are not). **No config plugin exists or is needed** — no `app.plugin.js` in the package; it autolinks like any RN library, so a normal prebuild/dev-build picks it up ([Expo install guide](https://www.revenuecat.com/docs/getting-started/installation/expo)).
- Dev build mandatory: "To use and test RevenueCat with Expo, you'll need to create an Expo development build"; after installing "you **must** run the full build process" — "Hot reloading without building will result in errors" ([Expo install guide](https://www.revenuecat.com/docs/getting-started/installation/expo)). Expo's own guide agrees: IAP libraries cannot run in Expo Go, create a development build ([docs.expo.dev/guides/in-app-purchases](https://docs.expo.dev/guides/in-app-purchases/)).
- Expo Go: SDK ships a **Preview API Mode** — native calls replaced by JS mocks so the app loads, but "real purchases will not function in this mode" ([README](https://github.com/RevenueCat/react-native-purchases#readme), [Expo install guide](https://www.revenuecat.com/docs/getting-started/installation/expo)).
- New Architecture: no official support statement exists in README, CHANGELOG, or docs (verified absent). The iOS module is a legacy bridge module (`RCT_EXPORT_MODULE` in `ios/RNPurchases.m`, zero `TurboModuleRegistry` usage in the repo), i.e. it runs on New Arch via RN's interop layer. One open crash report specific to **iOS 26 beta** + New Arch at interop registration time, open since 2026-04-01 ([issue #1712](https://github.com/revenuecat/react-native-purchases/issues/1712)).
- Web bundle: importing does **not** break react-native-web. v9.0.0 (2025-07-18) added a web target: "our libraries will work when you try to run your react native app on web. However, they will just respond with hardcoded fakes for now" ([v9.0.0 notes](https://github.com/RevenueCat/react-native-purchases/releases/tag/9.0.0)); `package.json` ships a `browser` entry and optional `react-native-web` peer. Real web support exists only through Web Billing (Stripe), and even then "operations `getProducts`, `purchaseProduct` or `restorePurchases` won't work on web environments" ([RN install guide](https://www.revenuecat.com/docs/getting-started/installation/reactnative)).

**For Mentis:** pin 10.x, nothing to add to `app.json`; the existing dev-build flow is exactly the supported path. Import is web-safe, but with no Web Billing configured, guard `Purchases.configure()` (and all premium UI) behind `Platform.OS !== "web"` so web never talks to a fake or throws on a native-only key.

## 2. Identity: Supabase uid as app user ID

- Two modes: pass the ID "on instantiation to Purchases" if known at launch, else call `.logIn()` later; by default the SDK generates anonymous IDs ([identifying customers](https://www.revenuecat.com/docs/customers/identifying-customers), [user IDs](https://www.revenuecat.com/docs/customers/user-ids)).
- `logIn()` from an anonymous ID merges/aliases: anonymous and provided ID get CustomerInfo merged — unless the provided ID already has an anonymous alias, in which case "No merge or purchase transfer occurs" ([identifying customers](https://www.revenuecat.com/docs/customers/identifying-customers)). `logOut()` "will generate a new anonymous App User ID for the logged out state".
- For sign-in-required apps the docs are explicit: "Only configure the SDK with a custom App User ID, and never call `.logout()`" — configure after the user ID exists rather than at app launch ([identifying customers](https://www.revenuecat.com/docs/customers/identifying-customers)). This sidesteps every aliasing pitfall: no anonymous IDs are ever created.
- Never hardcode an ID; emails discouraged (guessability, GDPR), advertising IDs discouraged (rotation) — an opaque backend uid like Supabase's is the recommended shape ([identifying customers](https://www.revenuecat.com/docs/customers/identifying-customers)).
- Cross-device/restore transfer: default restore behavior is **"Transfer to new App User ID"** — if user B restores on a device whose store account holds user A's subscription, "UserB would now have access to the subscription and it would be revoked from UserA"; alternatives: "Transfer if there are no active subscriptions", "Keep with original App User ID" (returns an error on foreign restore, "use with caution"), legacy "Share between App User IDs" ([restore behavior](https://www.revenuecat.com/docs/projects/restore-behavior)). A transfer emits a `TRANSFER` webhook ([event types](https://www.revenuecat.com/docs/integrations/webhooks/event-types-and-fields)).

**For Mentis:** configure only once a Supabase session exists, with the auth uid as app user ID; never call `logOut` (on sign-out, tear down/ignore the SDK instead). Keep default transfer behavior; the API must handle `TRANSFER` (premium moves from uid A to uid B) rather than assume entitlements only ever appear.

## 3. Modeling: one entitlement, one product per store, one offering

- Entitlements "represent a level of access, features, or content that a user is 'entitled' to"; attach products to them: "When a product that is attached to an entitlement is purchased, that entitlement becomes active for the duration of the product" ([entitlements](https://www.revenuecat.com/docs/getting-started/entitlements)). One entitlement `premium` with two attached products (App Store monthly, Play Store monthly) is the canonical single-tier setup.
- Offerings group packages; packages "abstract platform-specific products by grouping equivalent products across iOS, Android, and web" and carry a type (`MONTHLY`, `ANNUAL`, …) with convenience accessors (`.monthly`) ([displaying products](https://www.revenuecat.com/docs/getting-started/displaying-products)).
- Custom paywall fetch path: `const offerings = await Purchases.getOfferings()` → `offerings.current.availablePackages` (pre-fetched at launch, usually no network wait); `offerings.current` follows the project's default offering / targeting ([displaying products](https://www.revenuecat.com/docs/getting-started/displaying-products)).
- Localized price: each package's `storeProduct.priceString` — "Formatted price, including its currency sign, such as €3.99" — comes from the store already localized ([SDK type source](https://github.com/RevenueCat/purchases-hybrid-common/blob/main/typescript/src/offerings.ts)).

**For Mentis:** entitlement `premium`, products `premium_monthly` per store, one default offering with the monthly package; the custom paywall renders `offerings.current.monthly.product.priceString` and never hardcodes "€2.99".

## 4. Server surfaces for the NestJS API (facts only; push-vs-pull is #46)

- Webhook config (dashboard, per project): HTTPS URL, optional authorization header, environment (production/sandbox/both), and "(Optional) Filter the kinds of events that should be sent" ([webhooks](https://www.revenuecat.com/docs/integrations/webhooks)).
- Auth: set an authorization header value in the dashboard — "RevenueCat will send this header in every request"; verify it server-side. Stronger option: every delivery also carries `X-RevenueCat-Webhook-Signature` — timestamp + HMAC-SHA256 over the raw request body ([webhooks](https://www.revenuecat.com/docs/integrations/webhooks)).
- Delivery: usually 5–60 s after the event (cancellations up to ~2 h); 60 s response timeout; on failure "retry later (up to 5 times) with an increasing delay (5, 10, 20, 40, and 80 minutes)" then stops. "At least one delivery" — dedupe by event `id` (idempotent processing). Ordering is **not documented**; the retry ladder alone means a retried old event can land after a newer one, so process out-of-order-safe ([webhooks](https://www.revenuecat.com/docs/integrations/webhooks)).
- Docs' own sync recommendation (input for #46): call "the `GET /subscribers` REST API endpoint after receiving any webhook" to store state in one consistent format ([webhooks](https://www.revenuecat.com/docs/integrations/webhooks)).
- Events that matter for a premium-until-timestamp model ([event types](https://www.revenuecat.com/docs/integrations/webhooks/event-types-and-fields)): `INITIAL_PURCHASE`; `RENEWAL` ("an existing subscription was renewed, or a lapsed user resubscribed"); `CANCELLATION` (auto-renew off or refund — with refunds access ends, otherwise it runs to expiration; see `cancel_reason`); `UNCANCELLATION`; `EXPIRATION` ("the user's access should be removed"); `BILLING_ISSUE`; `PRODUCT_CHANGE`; `TRANSFER`; `SUBSCRIPTION_EXTENDED`; `TEST`. Every subscription event carries `app_user_id`, `original_app_user_id`, `aliases`, `entitlement_ids`, `product_id`, `purchased_at_ms`, **`expiration_at_ms`**, `store`, `environment` (`SANDBOX`/`PRODUCTION`), `period_type`, `cancel_reason`/`expiration_reason` — enough to maintain a `premium_until` column from the payload alone.
- REST v1: `GET https://api.revenuecat.com/v1/subscribers/{app_user_id}` "gets the latest Customer Info … or creates a new customer if it doesn't exist"; `Authorization: Bearer <key>`; no numeric rate limit published on the v1 reference ([API v1](https://www.revenuecat.com/docs/api-v1)).
- REST v2: `Authorization: Bearer sk_…` (secret key, server-only); customer-centric endpoints `GET /v2/projects/{project_id}/customers/{customer_id}` plus `/subscriptions` and `/entitlements` (active entitlements); adds `gives_access`, `auto_renewal_status`, `status`. Rate limits are published per domain — **Customer Information: 480 requests/minute** — with `RevenueCat-Rate-Limit-Current-Usage`/`-Current-Limit` headers on responses ([API v2](https://www.revenuecat.com/docs/api-v2), [authentication](https://www.revenuecat.com/docs/projects/authentication)).

**For Mentis:** whatever #46 decides, the API needs one HTTPS endpoint, a constant-time header check (+ optional HMAC), idempotency on event `id`, out-of-order tolerance, and a mapping from `entitlement_ids ∋ premium` + `expiration_at_ms` to `premium_until` keyed by `app_user_id` = Supabase uid.

## 5. Environments: sandbox vs production in one project

- One project serves both: "There's no concept of a sandbox or production _user_ in RevenueCat, since the same App User Id can have both production and non-production receipts"; "RevenueCat automatically detects the environment (production vs. sandbox) in which a purchase occurs, so no additional configuration is required" ([sandbox](https://www.revenuecat.com/docs/test-and-launch/sandbox)). Dashboard has a sandbox-data toggle; webhooks can be scoped production/sandbox/both; events carry `environment`.
- Public API keys are per app/platform within the project: "Each app under a project is automatically provided with a public API key" (one for the App Store app, one for the Play app — the SDK picks by `Platform.OS`); secret `sk_` keys are server-only ([authentication](https://www.revenuecat.com/docs/projects/authentication)). New projects start on a **Test Store** key for keyless early dev — must be swapped for the platform keys before production, "never Test Store API key" in a release ([sandbox](https://www.revenuecat.com/docs/test-and-launch/sandbox)).
- How a dev build hits sandbox (Apple): create Sandbox Testers in App Store Connect ("valid emails that you can verify you own"), enter them on device under `Settings > [Your Account] > App Store > Sandbox Account`; a development-signed build's purchases then run against sandbox — Apple prompts for the account at `purchase`/`restorePurchases`. Sandbox renewals are accelerated (1 month → 5 minutes); App Store caps sandbox receipts at 100 per customer. TestFlight is "a hybrid environment that uses production Apple Accounts but purchases occur in sandbox", renewing every 24 h since Dec 2024 ([Apple sandbox](https://www.revenuecat.com/docs/test-and-launch/sandbox/apple-app-store)).
- StoreKit Configuration files are supported (iOS 14+, simulator) with caveats: products in the file must also exist in RevenueCat, the test certificate must be uploaded to RevenueCat, and "StoreKit testing only works if you are running your app directly through Xcode" — no cancellation/refund events, incompatible with macOS ([Apple sandbox](https://www.revenuecat.com/docs/test-and-launch/sandbox/apple-app-store)).

**For Mentis:** the EAS/`expo run:ios` dev builds we already make hit sandbox automatically with a Sandbox Apple Account — no second RevenueCat project needed; StoreKit config files only pay off for Xcode-launched simulator runs, so plan on sandbox tester accounts as the main loop and let the API distinguish events by the `environment` field.

## 6. Pricing (as of 2026-08-21)

- Free: "Pay nothing for up to $2,500 in monthly tracked revenue"; beyond that, Pro at "1% of what you track"; Enterprise is custom ([pricing](https://www.revenuecat.com/pricing)).
- MTR "includes the revenue from all purchases and renewals including non-subscription products", measured before the store's cut; once over the threshold the 1% applies to the **full** MTR — "if you earned $2,600 in the previous billing cycle, you would incur a charge of $26"; billing periods anchor to the signup date, not calendar months ([account management](https://www.revenuecat.com/docs/welcome/set-up-revenuecat/account-management)).
- All features are included below the threshold — the free tier is not feature-gated ([pricing](https://www.revenuecat.com/pricing)).

**For Mentis:** at €2.99/month, $2,500 MTR ≈ 830+ concurrent paying subscribers before RevenueCat costs anything; past that it's ~$0.03 per subscriber-month. Cost is a non-factor for the MVP decision.
