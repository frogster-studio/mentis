# Supabase-only backend: direct RLS access, no API layer

Adding Google/Apple authentication and cross-device stat sync (the groundwork for the future social era: leaderboards, friend battles) required deciding what stands behind the app. Today the client reads Postgres directly through PostgREST with the anon key under RLS — there is no server code of ours anywhere. We keep that shape: Supabase Auth handles identity, and per-user data lives in new tables the client reads and writes directly under `auth.uid()` RLS policies. We rejected a standalone backend service (we would own hosting, deploys and token plumbing to rebuild what Auth + RLS give for free) and an edge-function write layer (a versioned API v1 does not need, plus cold starts); edge functions may still appear later for narrow jobs RLS cannot express. Consequence, accepted deliberately: a signed-in player can forge his own rows with his JWT — harmless while stats are private to their owner, but score integrity must be revisited before any leaderboard trusts these numbers, and real-time battles will layer Supabase Realtime and server-authoritative logic on top of this foundation rather than replace it.
